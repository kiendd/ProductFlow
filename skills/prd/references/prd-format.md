# ProductFlow document format

The single normative specification. `pf-validate` enforces everything below.

## 1. Directory layout

```
docs/
  product/
    PRD.md                 # type: product — whole-system overview
    index.md               # GENERATED by pf-index
    manifest.json          # GENERATED by pf-index — machine-readable map
    <domain>/
      PRD.md               # type: domain
      <capability>/
        PRD.md             # type: capability (one further level allowed)
  changes/
    <slug>/
      change.md            # why / what / scope / classification / design / outcome
      requirements.md      # delta: ADDED / MODIFIED / REMOVED / RENAMED
      tasks.md             # execution checklist
    archive/
      YYYY-MM-DD-<slug>/   # the three files above
.productflow/
  config.json              # committed
  runs/<slug>/progress.md  # execution ledger — gitignored
```

## 2. Frontmatter grammar

A strict subset, parsed by regex — not YAML.

- Line 1 is `---`; the block ends at the next line that is exactly `---`.
- Every line inside matches `^([a-z_]+): ?(.*)$`. No nesting, no multiline values, no comments,
  no blank lines, no duplicate keys.
- A value is either a raw scalar (trimmed) or an inline list `[a, b, c]` split on `,` and
  trimmed per item; `[]` is the empty list.
- Any violation is reported as `frontmatter-syntax`.

Key order when writing: `id`, `change`, `title`, `type`, `domain`, `parent`, `status`,
`classification`, `owner`, `created`, `updated`, `archived`, `domains`, `source_changes`,
`implements`, `tags`. Absent keys are simply omitted.

## 3. PRD document

```markdown
---
id: product.billing.invoicing
title: Invoicing
type: capability
domain: billing
parent: product.billing
status: active
owner: unassigned
updated: 2026-09-04
source_changes: [2026-09-04-add-invoice-pdf]
implements: [src/billing/invoice.ts]
---

# Invoicing

## Summary
<2–4 sentences: what this capability is, who it serves>

## Problem & Goals
<the problem, and measurable goals>

## Users & Use Cases
<personas and the situations they are in>

## Requirements

### REQ-BILLING-001: Xuất hoá đơn PDF
**Status**: active
**Statement**: Hệ thống PHẢI cho phép người dùng tải hoá đơn ở định dạng PDF.

#### Scenario: Tải hoá đơn hợp lệ
- **WHEN** người dùng bấm "Tải PDF" trên một hoá đơn đã phát hành
- **THEN** hệ thống trả về file PDF chứa đúng số hoá đơn và tổng tiền

## Behavior Details
<flows, states, error handling>

## Interfaces & Data
<APIs, schemas, config keys, events>

## Out of Scope
<boundaries>

## Implementation Map
| Requirement | Code | Tests |
|---|---|---|
| REQ-BILLING-001 | `src/billing/pdf.ts` | `tests/billing/pdf.test.ts` |

## Open Questions
<open questions, or "Không có">

## Change Log
| Ngày | Change | Tóm tắt |
|---|---|---|
| 2026-09-04 | add-invoice-pdf | Thêm REQ-BILLING-001 |
```

### Enforced rules

| Rule | Finding code |
|---|---|
| `id`, `title`, `type`, `domain`, `status`, `updated` are present | `frontmatter-missing-key` |
| `type` ∈ `product\|domain\|capability`; `status` ∈ `draft\|active\|deprecated`; `updated` matches `^\d{4}-\d{2}-\d{2}$` | `frontmatter-bad-value` |
| `id` matches `^product(\.[a-z0-9-]+)*$` | `frontmatter-bad-value` |
| `id` is derivable from the path: `docs/product/billing/invoicing/PRD.md` → `product.billing.invoicing`; `docs/product/PRD.md` → `product` | `id-path-mismatch` |
| All ten H2 sections present, exact names | `section-missing` |
| The ten sections appear in the canonical order | `section-order` |
| Requirement heading matches `^### (REQ-[A-Z0-9-]+-\d{3}): (.+)$`, followed by `**Status**:` and `**Statement**:` | `req-format` |
| Requirement ID unique across the whole `docs/product` tree | `req-duplicate` |
| Each requirement has ≥ 1 `#### Scenario: <name>` | `req-no-scenario` |
| Each scenario has ≥ 1 bullet containing `**WHEN**` and ≥ 1 containing `**THEN**` | `scenario-no-when-then` |
| Relative markdown links resolve to existing files | `link-broken` |

Retired IDs are never reused.

## 4. Requirement IDs

`REQ-<PREFIX>-<NNN>`.

- `<PREFIX>`: the first path segment of the domain, uppercased, with any character outside
  `[A-Z0-9-]` replaced by `-`. `identity/user-auth` → `IDENTITY`.
- `<NNN>`: three digits, ascending per domain.
- `pf-reqid` computes the next number from the highest ID found in `docs/product/**/PRD.md`
  **and** in every `docs/changes/**/requirements.md`, archive included. No state file; parallel
  changes cannot collide.

## 5. change.md

```markdown
---
id: add-invoice-pdf
title: Xuất hoá đơn PDF
status: draft
classification: architectural
created: 2026-09-04
domains: [billing]
---

# Xuất hoá đơn PDF

## Why

## What Changes

## Scope

### In scope

### Out of scope

## Impact

## Design

## Outcome
```

`status` ∈ `draft|planned|in-progress|implemented|archived`.
`classification` ∈ `bounded|architectural`.
`pf-archive` sets `status: archived` and adds `archived: <date>`.

## 6. requirements.md (delta)

```markdown
---
change: add-invoice-pdf
---

# Delta requirements

## ADDED Requirements

### REQ-BILLING-001: Xuất hoá đơn PDF
**Target**: product.billing.invoicing
**Status**: active
**Statement**: ...

#### Scenario: ...
- **WHEN** ...
- **THEN** ...

## MODIFIED Requirements

## REMOVED Requirements

## RENAMED Requirements
```

- All four H2 buckets are always present, even when empty.
- `**Target**` is the `id` of the destination PRD and is required for `ADDED` and `MODIFIED`.
- `MODIFIED` copies the **entire** new requirement — statement plus every scenario — not a diff.
- `REMOVED` requires `**Reason**:` and `**Migration**:`.
- `RENAMED` uses `**FROM**:` and `**TO**:` and keeps the ID.

## 7. tasks.md

```markdown
---
change: add-invoice-pdf
---

# Tasks

## 1. Renderer

- [ ] 1.1 Thêm hàm render PDF — verify: `pnpm test invoice-pdf`
  - Requirements: REQ-BILLING-001
  - Files: create `src/billing/pdf.ts`, create `tests/billing/pdf.test.ts`
  - Steps: viết test đỏ → chạy thấy fail → implement tối thiểu → chạy xanh → commit
```

Checkboxes match `^- \[( |x)\] (\d+\.\d+) (.+)$`. Every checkbox carries ` — verify: ` and the
three child lines `Requirements:`, `Files:`, `Steps:`. Violations are `task-format`.

## 8. Design and Outcome sections of change.md

`## Design` (filled by `productflow:plan`, only for architectural changes; left empty otherwise)
uses H3 sub-sections: `Context`, `Decisions`, `Risks & Trade-offs`, `Migration`,
`Open Questions`.

`## Outcome` (filled by `productflow:archive` at archive time) uses H3 sub-sections: `Shipped`,
`Requirements merged`, `Deviations from plan`, `Commits`, `Follow-ups`.

## 9. manifest.json

Generated by `pf-index`; never edited by hand.

```json
{
  "generated": "2026-09-04",
  "version": 1,
  "locale": "vi",
  "documents": [
    {
      "id": "product.billing.invoicing",
      "path": "docs/product/billing/invoicing/PRD.md",
      "type": "capability",
      "domain": "billing",
      "parent": "product.billing",
      "status": "active",
      "title": "Invoicing",
      "updated": "2026-09-04",
      "implements": ["src/billing/invoice.ts"],
      "requirements": [
        {"id": "REQ-BILLING-001", "title": "Xuất hoá đơn PDF", "status": "active", "scenarios": 1}
      ]
    }
  ],
  "changes": {
    "active": [{"slug": "add-invoice-pdf", "title": "...", "status": "in-progress", "tasks_total": 6, "tasks_done": 2, "domains": ["billing"]}],
    "archived": [{"slug": "add-invoice-pdf", "archived": "2026-09-04", "path": "docs/changes/archive/2026-09-04-add-invoice-pdf"}]
  }
}
```

`documents` sorted by `id`, `requirements` sorted by ID, JSON indent 2, trailing newline — so
diffs stay stable. A stale file is reported as `manifest-stale`.

`index.md` is generated alongside it, always beginning with
`<!-- generated by pf-index; do not edit -->`, with labels in the configured locale.

## 10. config.json

```json
{
  "version": 1,
  "docs_root": "docs/product",
  "changes_root": "docs/changes",
  "prd_locale": "vi",
  "requirement_prefix": "REQ"
}
```

Every script reads this file; a missing file exits `7`. `prd_locale` accepts `vi` or `en`;
anything else falls back to `en` labels with a warning.
