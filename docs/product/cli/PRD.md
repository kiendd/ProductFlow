# Command-line tools

## Summary

The CLI is six Python executables in `skills/productflow/scripts/`. They scaffold a repository,
allocate requirement IDs, regenerate the index, validate the tree, and archive a finished change.
Each walks up from the working directory to the folder holding `.productflow/config.json` and
reports every result as one JSON line on stdout, with a process exit code the caller can branch on.

## Problem & Goals

Agents and humans need the same deterministic operations on the docs tree, callable from scripts
and from a skill. The goal is a tool whose exit codes are a stable contract and whose generated
output diffs cleanly.

## Users & Use Cases

- A developer running `pf-init` once to adopt ProductFlow, then `pf-validate` in a git hook.
- An agent running `pf-new-change`, `pf-reqid`, `pf-index`, and `pf-archive` from inside a skill.

## Requirements

### REQ-CLI-001: Initialize a repository once
**Status**: active
**Statement**: `pf-init` MUST create the config, the product docs skeleton, and the changes
folder on first run, and MUST refuse a second run with exit code 3 without changing anything.

#### Scenario: First init creates the skeleton
- **WHEN** `pf-init --locale vi` runs in a repository with no `.productflow/config.json`
- **THEN** it exits 0 and creates `.productflow/config.json`, `docs/product/PRD.md`,
  `docs/product/manifest.json`, `docs/product/index.md`, and a `.gitignore` entry for
  `.productflow/runs/`

#### Scenario: Second init is refused
- **WHEN** `pf-init` runs again in an already-initialized repository
- **THEN** it exits 3 and changes no files

### REQ-CLI-002: Scaffold a change folder
**Status**: active
**Statement**: `pf-new-change <slug>` MUST create a change folder with `change.md`,
`requirements.md`, and `tasks.md`, reject a duplicate slug with exit code 4, and reject a
malformed slug with exit code 2.

#### Scenario: New change is scaffolded
- **WHEN** `pf-new-change add-invoice-pdf` runs
- **THEN** it exits 0 and creates `change.md`, `requirements.md`, and `tasks.md` under
  `docs/changes/add-invoice-pdf/`

#### Scenario: Duplicate slug is rejected
- **WHEN** `pf-new-change add-invoice-pdf` runs a second time
- **THEN** it exits 4 and leaves the existing folder untouched

#### Scenario: Malformed slug is rejected
- **WHEN** `pf-new-change Bad_Slug` runs
- **THEN** it exits 2 and creates nothing

### REQ-CLI-003: Allocate collision-free requirement IDs
**Status**: active
**Statement**: `pf-reqid <domain> --count N` MUST print the next N unused requirement IDs for the
domain in ascending order, one per line, computed from every PRD and every change delta including
the archive.

#### Scenario: Sequential IDs for an empty domain
- **WHEN** `pf-reqid billing --count 2` runs in a tree with no billing requirements
- **THEN** it prints `REQ-BILLING-001` then `REQ-BILLING-002`

### REQ-CLI-004: Regenerate the index and manifest
**Status**: active
**Statement**: `pf-index` MUST regenerate `docs/product/index.md` and
`docs/product/manifest.json` from the current PRD tree, with the generated marker in the index and
every PRD's requirements mapped in the manifest.

#### Scenario: A PRD and its requirements are mapped
- **WHEN** `pf-index` runs against a tree containing a PRD with `REQ-BILLING-001`
- **THEN** `manifest.json` contains `REQ-BILLING-001` with its scenario count, and `index.md`
  begins with the `generated by pf-index; do not edit` marker

### REQ-CLI-005: Archive only a finished, merged change
**Status**: active
**Statement**: `pf-archive <slug>` MUST refuse a change with unchecked tasks (exit 5) or an
unmerged delta (exit 6), and otherwise MUST set `status: archived`, add the `archived` date, and
move the folder under `docs/changes/archive/<date>-<slug>/`.

#### Scenario: Open tasks block the archive
- **WHEN** `pf-archive add-invoice-pdf` runs while `tasks.md` still has an unchecked box
- **THEN** it exits 5 and moves nothing

#### Scenario: Unmerged delta blocks the archive
- **WHEN** `pf-archive add-invoice-email` runs while an ADDED requirement is in no PRD
- **THEN** it exits 6 and moves nothing

#### Scenario: A finished, merged change is archived
- **WHEN** `pf-archive add-invoice-pdf` runs with every task checked and the delta merged
- **THEN** it exits 0, the folder moves to `docs/changes/archive/<date>-add-invoice-pdf/`, and that
  `change.md` reads `status: archived` with an `archived` date

### REQ-CLI-006: Locate the repository root from any subdirectory
**Status**: active
**Statement**: Every `pf-*` command MUST find the repository root by walking up to the directory
containing `.productflow/config.json`, and MUST exit 7 when no such directory is found.

#### Scenario: Run from a nested directory
- **WHEN** a `pf-*` command runs from a subdirectory below the repository root
- **THEN** it operates on the tree rooted at the directory containing `.productflow/config.json`

#### Scenario: Run outside an initialized repository
- **WHEN** a `pf-*` command runs where no ancestor holds `.productflow/config.json`
- **THEN** it exits 7

## Behavior Details

Each command prints one JSON summary line on stdout; `pf-validate` additionally accepts `--json`.
Shared exit codes: 2 usage error, 7 not initialized.

## Interfaces & Data

- Executables: `pf-init`, `pf-new-change`, `pf-reqid`, `pf-index`, `pf-validate`, `pf-archive`.
- Config read by every command: `.productflow/config.json`.
- Full contract: `skills/productflow/references/cli.md`.
